# Security

The intended product is read-only. It must not request private keys, sign transactions, submit on-chain writes, or expose provider credentials to browsers.

Provider access runs only in Supabase Edge Functions behind narrow adapters. Secrets stay in Edge Function or GitHub Actions configuration. `EVM_ETHEREUM_RPC_URL` and `SOLANA_RPC_URL` are read only by `wallet-sync`; logs and responses never include them. The browser may receive only the Supabase URL and publishable public key. Edge functions authenticate scheduled requests with a shared `CRON_SECRET` header compared in constant time (`supabase/functions/_shared/timing-safe-equal.ts`), so response timing cannot be used to guess the secret byte by byte.

Supabase tables must enable row-level security, and every table does as of its creating migration. Anonymous and authenticated clients may select only an explicit allowlist of publication-safe views and RLS-filtered base tables (see the `to anon` / `to authenticated` grants in `supabase/migrations`) and must receive no insert, update, or delete policy. No table is ever exposed by a blanket `all tables in schema public` grant: `202608040001_anon_grant_guardrail.sql` resets privileges to that allowlist independent of migration history and installs `assert_anon_read_contract()`, a function that raises if any relation outside the allowlist is ever granted `select`. That function is checked by `packages/database/src/verify-production.ts` on every production verification run, so a regression is caught in CI/staging rather than in production. Privileged writes use server-side credentials only. There is no auth or admin system; curated changes flow through repository review, validation, and idempotent sync.
